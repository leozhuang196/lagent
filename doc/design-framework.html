内部 Agent 平台 · 设计框架

本文档描述平台的整体设计：架构分层、模块边界、各项能力模型、核心流程、业务接入方式与技术选型。内容自包含，实现阶段不需要另行查阅其他材料。 各项决策的候选方案与论证过程另有《技术设计文档》，本文只给结论。相关的产品旅程与界面结构见《PRD》，流程清单与覆盖情况见《流程地图》。

1 · 概述

1.1 系统定位

平台把自然语言描述的工作任务转换为一系列工具调用并执行完成，产出可直接使用的交付物。三个接入面：网页会话、飞书群内 @提及、内部系统的 HTTP 接口。

与对话式助手的区别在于它执行有副作用的操作——写文件、调用外部系统、发送消息。因此有风险的调用必须经人工审批，这一约束贯穿全部设计。

平台本身是 Pilotx AI Agent 平台的平台层，业务 Agent 运行其上，两层的边界见 §2.1 与 §10。

2.3 三种划分的关系

本文档出现三种划分，它们回答的是不同问题，互不重叠：

划分 回答什么 单位 位置
平台层 / 业务 Agent 层什么是代码，什么是配置代码 vs 数据§2.1
代码分层代码内部谁能依赖谁包 / 目录§3.1
部署单元线上跑几个进程进程§2.2

第一层关系：代码五层全部属于平台层。 业务 Agent 层不含代码，它是数据库中的配置记录。因此这两个划分不在同一维度上——五层是平台层的内部结构，业务层是平台层的输入数据。

第二层关系：五层在进程内部。 §2.2 那张图画的是进程与它连接的外部依赖，五层画的是进程内部的代码结构——两者不在同一维度。把执行引擎剖开看：

第三层关系：四个部署单元是同一份代码的不同启动角色，不是四个独立工程。 每个单元只加载五层中的一部分：

读法：层是横切的（按职责切代码），部署单元是纵切的（按运行角色切进程）。

两条由此推出的实际约束：

  • 能力层只在执行引擎中加载。 API 服务与队列 Worker 不执行工具，因此不需要 MCP 客户端与连接器——这也意味着工具凭证只需下发到执行引擎，其余单元无需持有。
  • 飞书接入不含规则层与能力层。 它收到事件后只做落库与投递，不做任何判断（§9.18 要求回调立即返回）。

2.5 设计原则

原则 含义
P1 计算层无状态计算节点不长期持有会话状态，状态一律落在共享存储
P2 协调职责外置分布式锁、租约、信令由 Redis 承担，数据库只做记录读写
P3 人工介入必须可恢复需人工处理的事项持久化到待办服务，不依赖内存态挂起，可跨断连、重启与实例恢复
P4 外部依赖皆可替换存储、密钥、对象存储统一走接口，具备本地替代实现
P5 接口取能力交集面向可替换后端的接口只使用各实现的公共能力，不暴露任一实现的独有特性

每一层放什么

一词概括：接入层翻译，编排层调度，规则层判断，能力层动手，基础设施层存取。

层 放什么 判据
接入层 interface协议转换：HTTP 路由、SSE 推送、飞书长连接只把外部请求翻译成内部调用，不含任何业务判断
编排层 orchestration决定"什么时候做什么"：驱动轮次、调度步骤、派发子任务它掌握顺序与时机，规则问规则层，动作交能力层
规则层 rules规则与判断测试需要起数据库吗？需要就不属于这一层
能力层 capabilityagent 可以调用的东西：工具、连接器、MCP模型看得见，能在调用规格里选择它
基础设施层 infra平台自己运行要用的设施：存储、队列、事件流、模型网关模型看不见，它不知道这些存在

两处容易混淆，单独说明。

规则层是什么

把一次工具调用拆成四件事，每层只负责一件：

谁负责 做什么
调度编排层决定现在该做哪一步
取基础设施层从库里读出需要的数据
判断规则层拿到数据后算出结论
动手能力层真的去调用外部系统

规则层只做"判断"这一件事。 它被调用时，需要的数据已经由别人取好并作为参数传进来；它算出结论后返回，后续动作由别人执行。它自己不读库、不发请求、不改变任何外部状态。

体现在函数形状上：

属于规则层：
    判定(工具风险等级, 会话权限模式) → 直接执行 / 需人工介入
    两个入参都是值，返回一个结论。跑它不需要数据库、不需要网络。

不属于规则层：
    判定并执行(工具名, 会话标识) → 执行结果
    它要先查会话、查工具元数据、再执行——一个函数里混了取、判断、动手三件事。

一次完整走查：模型请求调用「发送飞书消息」。

  1. 编排层发现模型请求了工具调用，需要判断能否执行
  2. 编排层向基础设施层取数据：这个会话的权限模式是什么（读库）
  3. 编排层向能力层取数据：这个工具的风险等级是什么（读注册表元数据）
  4. 编排层把两个值交给规则层：判定(外部副作用, 逐项询问) → 需人工介入
  5. 规则层返回结论。它全程没有读过任何东西
  6. 编排层据此行动：写待办项（基础设施层）、挂起轮次

规则层在第 4 步被调用，前后都不参与。

规则层里有哪些

放的是"给定输入直接算出结果"的部分：

模块 输入 输出
permission工具风险等级 + 会话权限模式直接执行 / 需人工介入
compaction消息列表 + 预算上限压缩边界位置（须落在轮次边界上）
memory多个记忆空间的条目 + 优先级 + 预算合并去重截断后的条目列表
agent角色定义 + 记忆条目 + Skill 描述系统提示词 + 允许调用的工具名清单
approval待办项当前状态 + 提交的处理结果状态迁移是否合法、是否已被他人处理

不属于规则层的：读会话历史（repository）、调模型（model_gateway）、执行工具（能力层）、决定循环调用顺序（turn）、解析 HTTP（接入层）。

隔离这一层的实际收益：上表五项恰是最需要测试覆盖的部分——权限判错是安全事故，压缩边界切错会使模型收到残缺的工具调用结构。若它们与数据库、网络耦合，测试需拉起完整依赖，实际结果是覆盖不全。

这一层在有些架构方法（DDD）里叫"领域层"。本文档不用那个叫法，也不采用那套建模方式（聚合、值对象、领域事件）——本系统的复杂度在分布式执行，不在业务建模。

能力层与基础设施层的区别在于模型是否可见。 工具、连接器、MCP 属能力层，模型能看到它们的调用规格并选择调用；存储、队列、事件流、模型网关属基础设施层，模型不知道它们存在。因此 model_gateway（平台用于调用模型）在基础设施层而非能力层。

依赖约束

依赖只能向下。四条约束可在 review 阶段机械检查：

# 约束 违反后果
R-1规则层不得引入存储、协议、厂商 SDK规则无法脱离环境单测；权限判定、压缩边界这类最需覆盖的逻辑变得难测
R-2接入层不得直接访问存储，须经编排层或规则层鉴权与审计被绕过
R-3基础设施只被接口依赖，实现在启动时注入主库引擎可插拔无法落地；本地开发失去轻量替代
R-4能力层不得依赖编排层工具可反向驱动执行轮次，递归失控

R-4 是「禁止递归派生」（§9.3）在代码结构上的保证：子任务分发属编排层，工具属能力层，能力层不能向上依赖，该调用在结构上不可表达，无需运行时检查。

4 · 执行模型

4.1 执行轮次

系统的核心是一个循环：把一句自然语言请求转换为一串工具调用。

用户："把上周渠道数据汇总成表格"
   ↓
模型：需要先查数据 → 请求调用「查询工具」
   ↓
系统：只读操作 → 直接执行 → 结果回填上下文
   ↓
模型：请求调用「写文件工具」
   ↓
系统：写盘操作 → 挂起等待审批 → 批准后执行
   ↓
模型：不再请求工具 → 循环结束

一次「用户提交 → 循环跑到模型不再请求工具」的完整过程称为一次执行轮次，它是系统中唯一的执行单元。子任务分发与流程模板的每个步骤都是一次标准执行轮次，不存在第二套执行模型。

由此得到两个推论：

  • 编排层无需单独实现权限判定、审批、审计与崩溃恢复，这些能力直接继承。
  • 轮次这条链上的任何缺陷会在所有编排场景中等比放大。

循环结构本身简单，复杂度来自四处：模型调用需流式、工具可能产生外部副作用、任务时长可能超过客户端在线时间、系统需多实例部署。

完整时序见 §9.1。

4.2 上下文重建

引擎不持有会话。 每次轮次开始时从数据库读取会话历史重建上下文，结束即释放。会话生命周期可能长于进程（定时任务、跨重启场景），因此进程内不缓存会话状态（P1）。

客户端连接与执行解耦。 提交任务的 HTTP 请求在返回 202 时即结束，执行在后台进行。客户端断开、网络中断、前端崩溃均不影响任务，重连时凭事件序号补齐断连期间的事件（§9.2）。

上下文压缩在出站规模超过预算阈值时触发，仅改写发送给模型的内容，原始历史不修改。三项约束：触发阈值须预留余量（压缩本身需一次模型调用）、压缩边界须按轮次对齐（工具调用与其结果不可分离）、摘要须落库缓存（否则每轮重新生成，长会话成本线性叠加）。详见 §9.13。

4.3 装配：从角色算出提示词与工具清单

每次轮次开始，引擎要向模型发起一次请求。请求里有两样东西是这次会话专属的：

  1. 系统提示词 —— 一段文字，说明它是什么助手、按什么规则做事、掌握哪些背景
  2. 可调用的工具清单 —— 模型这次能选择调用哪些工具

而会话记录上只存了一个角色标识，例如「广告投放优化助手 v3」。从这个标识算出上面两样东西的过程，就是装配。

输入：角色标识 + 版本

  ↓ 读出角色定义，以及它引用的 Skill、记忆空间、工具集声明

输出：
  系统提示词 = 角色提示词 + 记忆条目 + Skill 的名称与描述
  工具清单   = 已注册工具 ∩ 角色声明的工具集
  另含：权限模式默认值、模型选择、可参与匹配的模板清单

换句话说，角色定义是"配方"，装配是"照配方把这次执行的初始状态配出来"。

版本在会话创建时固定，装配每轮次重建。 会话记录存的是角色标识与角色版本，而非角色内容的快照：不存快照是因为会话可能存活数天，快照会使角色变更对既有会话完全不可见；固定版本是因为运行中的会话不应因管理方修改角色而中途改变行为——与流程模板的处理一致（§9.17）。装配产物不落库（P1）。

输入 贡献
助手角色系统提示词主体、权限模式默认值、模型选择
Skill名称与描述拼入系统提示词，正文按需加载（§9.19）
记忆空间合并后的记忆条目拼入系统提示词
工具集声明允许调用的工具名清单
流程模板引用可参与匹配的模板清单

装配是纯函数，属规则层 rules/agent。由 R-1 与分层关系推出一个结果：规则层不能访问工具注册表（两者平级），因此装配只输出允许的工具名清单，由编排层持该清单向注册表取实际可调用对象。职责由此分开——装配判定可用范围，注册表解析名称到实现。

角色只能收窄，不能放宽

这是配置层与平台层之间的核心边界。角色声明的工具集是对已注册工具的过滤，不构成新的授权来源。

允许 不允许
从已注册工具中选取子集声明未注册的工具
将默认权限模式设得更严调低某个工具的风险等级
限制可用的流程模板范围使需审批的工具变为不需审批

风险等级只由平台基础表与用户级覆盖决定（§8.1），角色配置对其没有写入权。不守住这条边界，一份业务配置即可使审批机制失效。

需说明的现状：一期无身份体系，配置的写权限实际等同于共享口令的持有权。这与「共享密钥叠加默认全自动权限模式」属同一类问题，需一并接受或一并收紧。

角色的来源

触发路径 角色来源
使用者发起会话请求指定，未指定用默认角色
定时任务任务定义声明
流程模板步骤步骤声明；未声明则继承本次运行发起时的角色

第三条意味着流程模板可跨角色编排（分析角色取数 → 创意角色成文），因为每个步骤本身是一次独立执行轮次。由此产生一条调度约束：派发步骤时须连同角色标识与版本一同派发，并记入步骤运行记录，否则事后无法复现该步骤当时的配置。

角色定义是人工配置，但调用时不必手动指定。 网页输入框与飞书 @提及 均使用默认角色，使用者无需先了解有哪些角色。显式指定是可选路径（从流程库进入、或为某个群绑定固定角色）。

角色不由模型自动判定

"根据输入内容自动选择合适的角色"这一需求需拆成两半，两半的结论相反：

能否自动
知识适配：这次任务该带哪些背景知识可以，且机制已存在
能力边界：这次能调哪些工具、遇风险操作是否询问不可以

能力边界不自动判定，理由三条：

  1. 角色决定权限模式与工具集，判错即权限判错。 这与"自动套用流程模板"属同一类风险，而后者已明确不做（匹配到亦须使用者确认）。角色的影响面更大——模板只决定步骤，角色决定能否调用某个工具。
  2. 不可复现。 角色版本在会话创建时固定正是为了行为稳定；若角色本身由模型判定，同一输入两次提交可能落到不同角色。
  3. 审计断链。 事后追溯"为何本次可调用该工具"，答案将变成"模型判断应使用该角色"。

知识适配那一半由 Skill 机制承担。 通用角色将全部 Skill 的名称与描述常驻上下文，模型判断需要哪个即调用 load_skill 取回正文（§6.3）——这本身就是按输入内容自动适配。因此"通用 Agent"的实现形态是：默认角色（较宽的工具集 + 保守的权限模式）+ Skill 按需加载，不需要额外机制。

确实需要切换到专门角色的场景，本质是需要某个专属工具，而那正是不应自动决定的部分。此类情况走建议 + 确认：平台匹配到候选角色后提示切换，由使用者确认，与模板匹配的处理一致。

4.4 权限判定与人工介入

每次工具调用在执行前经权限判定，输入为工具的风险等级与会话的权限模式，输出为直接执行或需人工介入。判定逻辑是纯函数，属 rules/permission。

需人工介入时轮次挂起。挂起不是内存态等待：待办项落库，当前请求随即结束，恢复由之后另一次独立请求触发，且可能落在其他实例上（P3）。这是定时任务在无人值守时段产生的审批能在次日被处理的前提。

人工介入分两类，共用同一套机制：审批（授权一次有风险的调用）与提问（补充缺失信息）。分发与回收流程见 §9.5。

5.1 两条路径

5.2 执行图

流程定义为 JSON 声明式文档，含参数定义与步骤列表，步骤间以依赖标识构成有向无环图。声明式的选择理由是可静态校验（无环、引用存在）且无执行安全问题；不采用"定义即代码"，因其要求执行用户提交的代码，与进程级软隔离的隔离方案冲突。

fan-out：步骤可声明按列表型参数展开，运行时对列表中每个元素生成一个步骤实例并行执行。展开在运行启动、参数已知时一次性完成，此后图结构固定，调度与幂等控制均按展开后的实例进行。

模板运行启动的四步顺序不可交换：参数收集 → 冻结非确定量 → fan-out 展开 → 定图落库。展开源是参数，而参数可能由相对周期解算而来，因此展开须在冻结之后；图结构固定的前提是实例已生成，因此定图须在展开之后。顺序颠倒会使各并行实例各自取得时间基准，跨零点的长流程中不同实例将看到不同周期（§9.6）。

5.3 幂等、指纹与复用

需区分两类重复，成因与手段均不同。

重复投递 重复执行
成因队列至少一次投递语义重跑失败流程、改版后重跑
范围单次运行内跨运行
手段状态条件更新内容寻址的结果复用

领取的原子性：消费方以条件更新将步骤由「已派发」置为「执行中」，仅当更新成功才实际执行。因此这两个状态必须区分，不可合并。

步骤指纹：

step_key = hash( 定义标识 + 定义版本 + 步骤标识 + 展开元素 + 解析后的输入 )

"解析后的输入"指指令模板中全部引用代入实值之后的结果，即该步骤实际执行的内容。指纹相同即语义相同，可复用既有结果。由此得到断点续跑、改版后最小重跑、重复触发收敛三项能力（§9.7）。

含外部副作用的步骤不参与复用，指纹命中亦重新执行并重新审批——副作用是否已发生无法从指纹推断，该标记须在工具元数据中显式声明。

确定性约束：一切非确定量须在运行启动时求值一次并冻结进运行记录，步骤只能引用冻结值。否则指纹每次变化使复用永不命中，且重跑结果与原次不一致。该约束应在定义提交阶段校验拒绝，而非运行期暴露。

5.4 失败、超时与取消

失败判定有四个来源：工具报错、步骤超时、结果体超长、交付物归档失败。四者统一走同一套重试与策略分支。

重试不改变步骤指纹（同一步骤、同一输入），因此重试计数记在同一条步骤运行记录上，不新建实例。重试须退避，含外部副作用的步骤重试次数为零。

失败策略三种：中止整体（默认）、跳过后继、继续。fan-out 的失败策略作用在实例级，后继步骤的等待语义作用在步骤级——"多路检索允许个别路失败"的实现是实例级策略「继续」加步骤级等待全部实例终态。

三层超时须满足严格不等式：

模型调用超时  <  步骤超时  <  流程超时

不等式不成立将产生孤儿执行：步骤已判失败、调度器已向下推进，而该次模型调用仍在进行并将在稍后返回，结果写入一个已终态的步骤。

取消的语义是停止推进，不是回滚。 已发出的外部副作用无法撤回，中断只能保证不再执行后续操作。接口与产品文案均不得表达为"已撤销"。

6 · 扩展体系

6.1 工具注册

三类来源——内置工具、连接器、MCP 服务——注册为同一形态：一个可调用对象、一份调用规格、一组元数据（名称、分类、风险等级、是否需审批）。编排层只面向注册表，不感知工具来源。

采用注册表而非继承体系，使新增工具不触及编排层，且 MCP 工具与内置工具走完全相同的权限判定与审计路径。代价是元数据必须准确——风险等级标注错误将导致审批遗漏。

MCP 工具默认按外部副作用级别处理（需审批），放宽须显式配置。

6.2 MCP 与检索源

内部知识检索按常规方式经 MCP 接入，不作特例。但内置流程模板随平台版本发布，无法硬编码各部署环境的 MCP 服务名，因此引入一层间接：检索源是「MCP 工具 + 一组固定调用参数」的命名封装。

模板只引用检索源名，定义中不出现任何 MCP 服务名——更换后端服务只需修改检索源配置，模板不动。同一 MCP 服务可配置出多个检索源（仅参数不同），对模板而言它们是彼此独立的检索源。

MCP 与检索源是供给关系而非调用关系：它们在配置阶段就位，不在运行时被触发。配置变更时即刻回算模板的依赖可用性，该回算是模板可用状态的唯一来源（§9.9）。

6.3 Skill

Skill 是可复用的指令知识，与已有三类要素的区别：

内容 不是
工具可执行的代码不含做法知识
流程模板有依赖关系的步骤序列不适合表达无固定步骤的做法
助手角色一个 Agent 的身份与能力边界一份角色一套，无法跨角色复用
Skill一段指令知识，含名称、描述、正文与可选附件不是代码、不是流程、无身份

空位由此产生：多个业务 Agent 会共享大量做法知识（文案合规要求、归因口径定义、取数规范）。写入角色提示词则每个角色重复一份且长期占用预算；做成工具则无可执行代码；做成流程模板则它不是流程。

核心机制是按需加载：会话初始化时只将名称与描述注入上下文，Agent 判断需要时调用 load_skill 取回正文。若正文常驻，Skill 数量增加即会耗尽上下文预算，而这正是引入它所要避免的问题。

两点约束：正文只在本次会话生效，不写回持久历史（否则下一轮次重建上下文时会作为历史消息重复注入）；load_skill 虽为只读工具但必须进审计——它改变 Agent 的行为，不记录则事后无法解释某次执行的依据（§9.19）。

7 · 状态与一致性

多实例部署引入两个正确性问题，本章的机制均为应对它们。

7.1 执行租约

问题：同一会话并发执行会破坏消息历史。以进程内标记保证"一个会话同时只有一个轮次"在多实例下无效——实例 A 执行会话 X 时请求落到实例 B，B 判定空闲并启动第二个轮次，两者同时追加消息并持久化。这是数据正确性问题，非体验降级。

机制：以 Redis 原子写入抢占 session:lease:<会话标识>，执行期间续期，结束时释放。必须设置 TTL——进程被强制终止时不执行释放逻辑，无 TTL 将导致会话永久锁死。

续期失败须主动放弃轮次。 续期失败意味着租约可能已因 TTL 到期被他人抢占，此时继续写入即回到上述历史破坏场景，只是触发原因从判定失误变为存储抖动。

7.2 事件流

事件是引擎与外界之间的唯一契约。每个关键节点产出一个带单调递增序号的事件，写入带 TTL 的 Redis Stream，该 Stream 兼作实时分发通道与断连回放缓冲。

前端、内部系统与飞书回投消费的是同一份事件流。不为任一客户端增设专用通路，不以时间戳替代序号。

断连续传由 SSE 协议原生的 Last-Event-ID 承载，服务端按序号读取增量即可，无需自研心跳与重连协议（§9.2）。

7.3 跨实例信令

问题：中断须作用于持有该轮次的执行上下文。若轮次在实例 A 运行而中断请求落到实例 B，B 无法触及该上下文，中断将无声失败。

机制为双通道。Redis Pub/Sub 不保证投递——订阅方短暂断连期间发布的消息直接丢弃，因此取消不能只走信令：

  1. 在会话上写入持久化取消标记，执行引擎在每次轮次迭代之间检查；
  2. 发布控制信令，使执行中的模型流或工具调用尽快响应。

信令是加速通道，正确性由持久标记保证。 信令丢失只影响响应延迟，不影响取消最终生效。

审批类交互不需要该通道——它经待办服务持久化（P3），天然跨实例可用。

8 · 安全模型

8.1 风险分级与审批

每次工具调用按风险等级分类（只读 / 本地写入 / 命令执行 / 外部副作用），结合会话的权限模式得出是否需人工介入。风险等级只由平台基础表与用户级覆盖决定，配置层无写入权（§4.3）。

审批是整个安全模型的最后一道防线。其有效性依赖审批卡片能否让使用者在不询问他人的情况下判断操作后果，因此批准率与决策时长是监控项：批准率接近 100% 且决策时长极短即为盲批信号。

8.2 注入防护

Agent 系统的注入风险主要来自工具返回内容而非用户输入。用户输入本身即为指令，不构成注入；风险在于 MCP 服务或检索源返回的文本中夹带指令，该文本直接进入上下文，而 Agent 具备工具调用能力。

普通 LLM 应用被注入的后果是输出不当内容，Agent 被注入的后果是执行不当操作。该攻击面随 MCP 接入服务增多而扩大。

防护 做法
来源边界标记工具返回内容拼入上下文时显式标注为数据而非指令，并在系统提示词中约定数据区内容不作为指令执行
触发来源可见审批卡片须显示该次调用由哪一步、依据什么内容发起
来源不可提权工具返回内容不得降低后续调用的风险等级
外部地址白名单向外部地址发送数据的工具，目标地址取自配置而非模型产出

护栏不替代审批，而是减少审批疲劳。 注入攻击最终会撞上审批，前提是审批者能识别出该操作与其请求无关。

8.3 数据边界

密钥不得进入提示词、上下文与追踪记录。

业务敏感数据（个人信息、人群数据）需同等对待，但边界不同——它们是任务的处理对象，不能简单禁止。约束落在工具层：返回个人信息的工具默认返回聚合结果或标识引用；确需明文的场景由该工具单独声明，并按外部副作用级别处理。约束落在调用规格上因而可静态检查，不依赖模型自觉。

数值计算须由工具完成，模型只负责组织表述。模型自行计算的错误率不低且不可追查。约束落在两处：分析类角色的系统提示词明确要求计算调用工具；聚合类工具在返回结果中同时给出口径说明，供模型原样引用。

输出内容审核做成一类工具而非引擎内建钩子：审核服务经 MCP 接入，发布类工具在其调用规格中声明依赖审核结果。引擎侧只保证一点——声明需审核的工具在审核未通过时不得执行。

9 · 核心流程

本章为动态视图：19 条流程的时序、分支与实现要点。静态模型见 §4–§8。

先给两组跨流程的内容——共性规则与易错实现——它们分散在多条流程中，单独实现每条流程时容易各自发明一遍。

共性规则

状态迁移一律用条件更新，不用先读后写。 出现在步骤领取（§9.14）、待办项处理（§9.5）、租约抢占（§9.16）。三处形式一致：将状态由 X 改为 Y，只有更新成功的一方继续执行。任何"先查状态再决定是否写入"的实现均为缺陷。

"已被其他方处理"是正常态，不是错误。 出现在待办项被两个通道同时提交、步骤被两个 Worker 同时领取、租约被抢占。三处均应返回已处理及其结果，不得返回冲突错误。

含外部副作用的步骤永不复用、永远重新审批。 出现在断点续跑（§9.7）、重试（§9.14）、定时任务重叠（§9.11）。判据无法从步骤指纹推断，须在工具元数据中显式声明。

时间与随机须在运行启动时冻结。 出现在模板启动（§9.6）、续跑（§9.7）、定时触发（§9.11）。步骤内部读取当前时间的实现均为缺陷。三处表现不同（指纹不稳、跨零点周期不一致、重跑结果与原次不同），根因一致。

事件是唯一对外契约，序号是唯一顺序依据。 贯穿全部流程。不为任一客户端增设专用通路，不以时间戳替代序号。

子任务分发的强制约束（代码层限制，不依赖模型自觉）：

  • 单次分发的并行子任务数量设上限，超出直接拒绝，避免瞬时占满执行资源。
  • 子任务的工具集中不包含"子任务分发"能力本身，即禁止递归派生。

流程模板采用声明式描述（步骤 + 依赖关系 + 每步使用的助手角色与指令），不采用可执行脚本形式——声明式可静态校验、边界清晰。步骤间通过结构化的"步骤结果上报"传递产出，由后一步骤的起始指令注入。

9.5 审批与提问的分发与回收

触发：权限判定认为需人工介入（审批），或 Agent 缺少必要信息无法继续（提问）。两者共用同一套机制，仅事项类型不同。

核心判断：待办项是唯一事实来源，分发是镜像而非路由

9.6 模板运行的启动

前置校验不通过则拒绝启动，且不产生运行记录——避免管理界面里堆积一批从未真正开始的失败运行。校验项：定义存在且启用、依赖资产齐备（检索源 / 连接器）、必填参数齐备、各步骤声明的角色存在且启用。

步骤的角色：每个步骤可声明自己的助手角色，未声明则继承本次运行发起时的角色。因此模板可跨角色编排（分析角色取数 → 创意角色成文），每个步骤本身是一次独立执行轮次（§9.3）。派发步骤时要连同该步骤的角色标识与版本一起派发，并记入步骤运行记录，否则事后无法复现该步骤当时的配置（§4.3）。

时间基准 · 相对周期解算 · 随机值`"]
  D --> E{"存在 fan-out 步骤？"}
  E -->|否| G["④ 定图"]
  E -->|是| F["`③ 按列表长度展开实例

为什么顺序固定：展开源是参数，而参数可能由相对周期解算得到，所以展开必须在冻结之后；图结构固定的前提是实例已生成，所以定图必须在展开之后（流程定义的校验规则）。若先展开后冻结，各实例会各自取时间基准——跨零点的长流程里会出现"不同路看到不同周期"，且指纹不稳定导致复用永不命中。

一个可提前的动作：步骤指纹在定图时即可计算（此时输入已全部确定），不必等到派发。这样管理界面在运行开始时就能显示"本次有几步可复用"。

9.7 断点续跑与结果复用

「续跑」与「重新运行」必须区分为两个动作

动作 冻结量 指纹 效果
续跑沿用原运行的冻结量未改动的上游多能命中真正接着跑，只补做失败及其下游
重新运行重新冻结全部变化等价于全量重跑

这是确定性约束（§9.6 的冻结约束）推出的必然结论：冻结量参与指纹计算，沿用与否直接决定能否命中。 因此界面上不能只给一个「重跑」按钮——否则"为什么有时几秒就完成、有时又整跑一遍"无法向使用者解释。

flowchart TB
  A["使用者在运行记录上发起"] --> B{"续跑 or 重新运行"}
  B -->|续跑| C["新建运行，沿用原冻结量"]
  B -->|重新运行| D["新建运行，重新冻结"]

  D --> E

  F -->|否| I["正常派发执行"]
  F -->|是| G{"该步骤含外部副作用？"}

要点

  • 始终新建运行，不原地改写原运行——原运行是审计事实；且「部分成功」已产出的结果需要保留。
  • 含外部副作用的步骤永不复用（§9.7 的步骤指纹），即使指纹命中也重新执行并重新走审批。
  • 交付物复用的是引用，不复制对象存储中的文件。
  • 定义已改版时：改动步骤及其全部下游指纹变化、自然重跑；未改动的前缀命中复用——这就是 「追加写事件 + 步骤指纹」的持久化模型 所说的「最小重跑」，无需额外机制。

9.12 交付物的产出与归档

先修正一处会导致错误实现的表述

术语表原将交付物写作"会话结束时归档至对象存储"，而任务工作区是"单个会话专属的临时目录，会话结束后清理"。这两条放进流程里会引出错误实现——因为 本章「步骤即轮次」的约定 规定每个步骤对应一次独立会话，步骤 A 与步骤 B 的工作区互不可见；若"会话结束时归档"被理解为"整段对话结束时"，那么步骤 A 的工作区在其自身会话结束时早已清理，文件已经不存在了。

正确时机是「产出即归档」：在产出所在的那一次轮次 / 步骤结束、工作区清理之前完成归档。术语表已据此修正。

flowchart TB
  A["轮次 / 步骤在工作区内产出文件"] --> B["归档至对象存储"]
  B --> C{"归档成功？"}
  C -->|否| D["重试；仍失败则判定该步骤失败并告警"]
  C -->|是| E["`结果中携带交付物引用
不内联文件内容（「步骤结果只带引用不内联内容」的约定）`"]
  E --> F["清理工作区临时目录"]
  F --> G["后继步骤按引用读取"]
  G --> H["使用者 / 调用方经签名 URL 获取"]

要点：

  • 归档未成功不得判定步骤成功——否则后继步骤拿到失效引用，失败点会漂移到下游，排查时看到的是"步骤 B 读不到文件"而不是"步骤 A 归档失败"。这是 「归档失败导致产出丢失」这一风险 的具体落法。
  • 工作区清理必须在归档之后，顺序不可颠倒。
  • 一律经签名 URL 获取，不直连对象存储；有效期与交付物保留期需确定（有效期数值待定）。
  • 同名产出不覆盖——多次运行产生同名文件时以运行 / 步骤标识区分。覆盖会让"部分成功时已有产出保留"这条承诺失效。

约束 不遵守的后果
触发阈值须留出余量，不能等超出预算才压压缩本身要调一次模型，若已无余量则连压缩请求都发不出去，轮次直接卡死

  • 原始历史不改动（§4.2），因此界面上使用者看到的仍是完整过程——压缩对产品侧不可见。
  • 不影响步骤指纹：指纹算的是"指令模板代入实值后的结果"（§9.7 的步骤指纹），与历史是否压缩无关。
  • 压缩是有损的。保留原始历史只保证"人能回看"，不保证"模型能恢复"。因此对准确性敏感的长任务应优先走流程模板——每个步骤是独立会话、上下文天然短（本章「步骤即轮次」的约定），而不是让单个会话无限增长后依赖压缩兜底。这是 §9.3 两条编排路径之外的第三个选择依据。

  • 重试不改变步骤指纹（同一步骤、同一输入），因此重试计数记在同一条步骤运行记录上，不新建实例。否则运行记录里会出现多条看起来重复的步骤。
  • 重试须退避（指数退避 + 次数上限），避免对外部服务形成压制式重试；具体参数见 待压测确定的数值。
  • fan-out 的失败策略作用在实例级，后继步骤的等待语义作用在步骤级——这两层不要混。所以"三路检索允许个别路失败"的实现是：实例级策略为「继续」，步骤级仍等待全部实例到达终态（流程定义的校验规则）。
  • 「部分成功」需要一条明确规则（方案，需确认）：§9.14 的表述是"存在失败但有可用产出"，但"可用产出"由谁判定未定。建议采用可机械判定的规则——至少一个出度为零的步骤成功产出了交付物或结构化结果，即判定为部分成功；否则判定为失败。
  • 失败原因必须落进运行记录且对使用者可读，不能只留堆栈——无人值守任务的失败只能靠这条记录被理解。

9.15 超时与取消

三层超时必须满足不等式

模型调用超时  <  步骤超时  <  流程超时

这个不等式不成立就会产生孤儿执行：若步骤超时早于模型调用超时，步骤已被判定失败、调度器已往下走，而那次模型调用仍在进行并会在稍后返回——结果写给一个已经终态的步骤。同理，流程超时早于步骤超时会留下"流程已结束、步骤还在跑"的状态。

取消的传播

步骤当前状态 处理
待执行 / 已派发直接置为已取消，无需信令
执行中经控制信令中断对应会话（§9.16）
已终态不动，产出保留

中断在三个位置响应（§4.1）：模型流式输出中、工具执行中、轮次迭代之间。

取消不是回滚

已经发出的外部副作用无法撤回——消息已经发出、文件已经写入外部系统，中断只能保证"不再继续做下一件事"。因此：

  • 技术语义是停止推进，不是撤销。
  • 产品文案不得表达为"已撤销"或"已回滚"，否则使用者会以为副作用被清除了。正确表达是"已停止，已发生的操作不会撤回"。
  • 取消操作本身幂等：对已取消的运行重复取消无副作用、不报错。

超时后的最终状态判定与 §9.14 一致：按已产出结果判定为「部分成功」或「失败」。

9.16 执行租约与跨实例信令

sequenceDiagram
  autonumber
  participant API as API 服务
  participant R as Redis
  participant EA as 实例 A（执行中）
  participant EB as 实例 B（收到取消请求）
  participant DB as 主数据库

  API->>R: 原子写入 session:lease（带 TTL）
  alt 写入成功
    R-->>EA: 获得租约，开始执行
    loop 执行期间
      EA->>R: 续期
      alt 续期失败
        EA->>EA: 主动放弃本轮次，不再写入消息
      end
    end
  else 写入失败
    API-->>API: 已有轮次在执行，返回冲突
  end

  EB->>DB: 写入会话级「取消标记」（持久化兜底）
  EB->>R: 发布控制信令到 session:control
  R-->>EA: 信令送达（加速通道，不保证）
  EA->>EA: 在迭代间检查取消标记 → 中断
  EA->>R: 释放租约

续期失败与取消兜底

一、续期失败必须主动放弃轮次。 续期失败意味着租约可能已因 TTL 到期而被他人抢占。此时若继续执行并追加消息，就正好回到 §9.16 的执行租约与信令 问题一所描述的历史破坏场景——只是触发原因从"多实例判定失误"换成了"Redis 抖动"。因此续期失败的唯一正确处理是立即停止写入并放弃本轮次，交由恢复流程（数据模型）重新接管。

二、取消必须有持久化兜底，不能只依赖信令。 Redis Pub/Sub 不保证投递：订阅方短暂断连期间发布的消息直接丢弃。若取消只走信令，一次网络抖动就会让取消静默失效——这正是 「跨实例中断静默失效」这一风险 描述的风险，而"测试覆盖跨实例场景"是验证手段、不是设计对策。

因此取消请求同时做两件事：

  1. 在会话上写入持久化的取消标记——执行引擎在每次轮次迭代之间检查该标记；
  2. 发布控制信令——用于让执行中的模型流或工具调用尽快响应，而不必等到下一次迭代。

信令是加速通道，正确性由持久标记保证。 信令丢失只影响响应延迟，不影响取消最终生效。

其他

  • TTL 是必须的（§9.16 的执行租约与信令）：进程被强制终止时不会执行释放逻辑，无 TTL 会导致会话永久锁死。
  • 审批类交互不需要这条信令通道——它经待办服务持久化（§9.5，原则 P3），天然跨实例可用。

旧版本不能删，这是断点续跑推出来的约束

§9.7 的续跑要按原运行所用的定义版本重算步骤指纹。若旧版本被物理删除，该运行的指纹无从计算，历史运行就再也不能续跑了。因此：

  • 只允许停用，不允许物理删除。 停用后不能新起运行，但既有运行仍可续跑。
  • 内置层模板随平台版本发布、只读，不走本流程。

定时任务绑定哪个版本

这是之前的缺口，两种绑法都有明显问题：

绑法 问题
绑固定版本改了模板定时任务不生效，使用者会以为改动没保存
绑最新版本改模板后无人值守任务的行为静默改变——这对定时任务是危险的

方案（需确认）：绑定「模板标识 + 取最新已发布版本」，但版本变更时在「自动化」列表上给出显式提示——"该流程已更新，下次运行将采用新版本"。既不静默改变行为，也不让改动失效。

9.18 飞书凭证配置与长连接维持

  A["配置应用凭证"] --> B["存入密钥存储（密钥集中存放的约定）"]
  B --> C["`各实例发起出站长连接

  C --> D["事件到达任一连接"]
  D --> E["`立即入队 / 落库并返回

  E --> F["按 §9.4 路由到会话"]
  C -.掉线.-> G["`指数退避重连

  G -.全部掉线.-> H["告警（可观测性告警项）"]

事件回调与实例数上限

一、事件回调必须立即返回，不能在回调内同步执行轮次。 飞书长连接方案 明确"事件需在限定时间内处理完毕"，而一次执行轮次可能持续数分钟——若在回调里等轮次跑完，必然超时，飞书侧会判定投递失败并重试，结果是同一条消息被处理多次。因此接收后的唯一动作是落库/入队并立即返回，实际执行走正常的异步派发路径。

二、实例数受飞书单应用连接数上限约束。 飞书长连接方案 提到"单应用连接数上限"，其部署含义是——执行实例的水平扩容上限受此约束（每实例维持一个连接）。超过上限时多余实例无法建连，需要改为"部分实例持有连接、其余仅做执行"的形态。这是一条需要写进部署文档的硬约束。

其他

  • 事件处理逻辑与实例无关，因此"消息投递至任一连接"（非广播）不需要选主或连接归属路由（飞书长连接方案 已确认）。
  • 话题与会话的绑定关系持久化，保证重启后仍能正确路由。
  • 凭证轮换时重建连接；旧连接自然断开。

9.19 Skill 的注入与按需加载

flowchart TB
  A["会话构建：取助手角色"] --> B["读该角色引用的 Skill 列表"]
  B --> C["`只取名称与描述
不读正文`"]
  C --> D{"`名称描述 + 记忆
超出注入预算？`"}
  D -->|是| E["`按优先级截断
并留可观测记录`"]
  D -->|否| F["拼进系统提示词"]
  E --> F
  F --> G["轮次开始"]
  G --> H{"Agent 判断需要某个 Skill？"}
  H -->|否| I["正常执行"]
  H -->|是| J["调用 load_skill（只读，不需审批）"]
  J --> K["`读正文与附件引用
进入本轮上下文`"]
  K --> L["记审计：本次加载了哪些 Skill"]
  L --> I

要点：

  • 注入阶段只读描述，这是按需加载能省下预算的前提。若把正文也注入，Skill 一多就会撑爆预算，而这正是引入它要避免的问题（§9.19）。
  • 描述与记忆共享同一份注入预算（§9.19 的注入预算）。两者相加才是注入总量，截断规则也共用。
  • 正文只在本次会话生效，不写回持久历史——否则下一轮次重建上下文时会把它当历史消息重复注入。
  • load_skill 要进审计。它是只读工具，但会改变 Agent 的行为，不记录就无法事后解释"这次它为什么这么做"。

与流程模板的分工：模板管"分几步做"，Skill 管"某一步该怎么做"。一个步骤的指令里可以引用 Skill，反过来不行——Skill 里不描述步骤依赖。

一个会话 = 一个长 workflow超长 event history 需 Continue-As-New；会话历史在主库已有一份，将重复存储
仅流程模板走 Temporal系统内并存两套执行路径，破坏「一个步骤 = 一次标准执行轮次」的统一性

若维持自研，将来切换的代价：workflow 模块对外仅暴露提交、查询、取消三个接口时，内部换引擎不影响调用方；但历史运行记录无法迁移——自研用步骤指纹与追加写事件，Temporal 用 event history，数据模型不同。切换只能新流程走 Temporal、老记录只读保留，且切换前的历史运行将失去断点续跑能力。

决策所需输入：12 个月内预期接入的业务 Agent 数量、是否有明确 SLA 要求、是否有专职基础设施维护投入。
